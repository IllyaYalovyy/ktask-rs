# Run storage limits

Every value below is a positive integer environment override, read by the runner and guardian. Invalid or zero values use the default. Restart or resume after changing a limit. Limits apply per attempt or worker unless stated otherwise.

| Variable | Default | Meaning |
| --- | ---: | --- |
| `KTASK_ARTIFACT_FILE_BYTES` | 128 MiB | Largest archived file |
| `KTASK_ARTIFACT_ATTEMPT_BYTES` | 1 GiB | Archived bytes per attempt, including reservations |
| `KTASK_ARTIFACT_ATTEMPT_FILES` | 4096 | Archived files per attempt, including empty files and reservations |
| `KTASK_ARTIFACT_SCAN_ENTRIES` | 256 | Most top-level artifact entries examined per worker; extras make evidence incomplete |
| `KTASK_OUTPUT_BYTES` | 64 MiB | Persisted stdout, stderr and system text per attempt |
| `KTASK_OUTPUT_ROWS` | 100,000 | Persisted output rows per attempt, including empty rows |
| `KTASK_SCRATCH_BYTES` | 4 GiB | Logical file bytes or allocated blocks, whichever is larger, including directory blocks, in one managed worker scratch directory |
| `KTASK_SCRATCH_ENTRIES` | 200,000 | Files and directories in one managed worker scratch directory |
| `KTASK_RUNNER_LOG_BYTES` | 8 MiB | One detached runner log segment; one previous segment is retained |

Output and artifact admission reject a write before it enters state storage. Output bytes and rows have transactional per-attempt counters; an upgraded attempt initializes its counters from retained output once, including empty rows and UTF-8 bytes. A shared instance admission watermark serializes producers across projects and conservatively claims SQLite/WAL growth, publication directories and pending artifacts, leaving recovery headroom. Housekeeping reconciles the watermark with physical allocation when no admission intervenes. Already saved output, files, checks and history remain available. An exceeded limit pauses the attempt as a resource condition; raising the limit or freeing capacity permits resume without a coding repair round. A check transcript that cannot be archived is incomplete evidence and cannot pass verification.

The guardian samples managed scratch every 250 ms throughout the producer's lifetime, including after stdout and stderr close, and checks again after the producer exits. Output delivery uses bounded in-memory queues (the supervisor's reader buffers up to 1,024 chunks so a shared-database commit delayed by many concurrent projects does not back up the guardian); if the supervisor cannot accept a message for two seconds, the guardian stops the producer and reports incomplete evidence. Delivery waits do not suspend scratch monitoring. If the final message cannot be delivered, dedicated guardian exit statuses preserve scratch, artifact, or delivery resource classification; the attempt pauses with an explicit incomplete-evidence reason. Resume requires fresh verification. The guardian stops and reaps the process group before archiving and cleanup. Scratch overshoot is the bytes and entries a producer can create during one 250 ms sampling interval, the directory scan, and process-group termination; the amount depends on the producer's write rate. This is a monitoring limit, not a filesystem quota. The scan short-circuits when either limit is exceeded. A detached logger process rotates stderr at a write boundary, so a segment can exceed its limit by one 4096-byte read plus the rotation marker. Existing segments are compacted to a lower configured limit at logger startup, retaining their most recent bytes and a marker. No excess output is sent to a secondary spool.

Project Storage has a separate retained-data policy: 30 days, 8 GiB allocated and 100,000 files/directories by default (a self-hosting instance's SQLite file alone can exceed 1 GiB). The minimum age is a hard floor: capacity pressure, automatic housekeeping and manual cleanup never delete younger evidence, so when protected or too-young data keeps the instance over budget the preview and the runner report the bytes protected by age, by reused-check references and by open work, and no new work launches until capacity is raised or the evidence ages out. `retention DAYS --max-bytes N --max-files N` changes it through the shared service; Configuration → Storage offers the same fields. Byte and entry limits measure the entire opened instance state root, including the shared SQLite database, WAL, evidence directories and rotated runner logs. The CLI and TUI distinguish logical evidence bytes, physically allocated bytes, eligible files, reusable SQLite pages and protected allocation. Each runner handoff performs bounded 64-item cleanup batches and visits at most 64 directory entries for physical reconciliation. SQLite database, WAL and SHM files are measured separately at scan completion because they can be recreated behind a saved directory offset. The no-follow scan cursor survives restart; output and artifacts admitted while it runs are added to its measurement instead of restarting it, and new work waits for the scan to settle. A step launch checks the projected allocation without reading output or walking the state tree. A queued run schedules more batches while eligible cleanup or reconciliation progresses. Reused-check sources, unresolved failures, live attempts and pinned evidence remain protected. Cleanup starts before the limit, reserving up to 256 MiB and 256 entries for recovery. If that reserve cannot be kept, the runner pauses additional work and reports the current allocation and cause. SQLite's incremental vacuum is enabled for new databases. A database created with auto_vacuum off is converted once by `VACUUM` at the runner's safe point, when no work is live in the instance and about three times the database size is free; until then the preview reports the limitation and its reason. The conversion is optional: a failure or too little space in SQLite's temporary directory defers it with the cause logged and shown, and never stops the queue. Files are deleted outside SQLite write transactions, between a short transaction recording the intent and another marking them pruned; a generated-path violation is skipped and reported without stopping housekeeping. One WAL checkpoint is attempted per housekeeping call and can be deferred by a concurrent reader.

The smallest configured byte and file limits among projects in one instance govern their shared allocation. Preview reports the effective limits whenever they differ from the current project's settings. Detached runner logs use a per-project segment cap that keeps their two rotated segments inside a quarter of this shared byte budget.

For budgets below 512 MiB, a new task starts only while at least half remains free for its startup records and subsequent recovery; in-step output and artifact admission retains a separate 25% recovery reserve. The launch reserve is capped at 256 MiB, and file-entry reserves at 256 entries. Cleanup can use recently closed evidence before the launch reserve is crossed, then continues with bounded SQLite page reclamation until starting work is safe.

## Build caches and diagnostic trees

Development builds multiply: Cargo keys artifacts by package version, so every version bump leaves a full set of test binaries, libraries, fingerprints and incremental state behind. ktask bounds what it can prove it owns and reports the rest.

**Ownership.** A directory is managed only when it holds `.ktask-cache-owner` *and* this instance's registry (`<cache>/owned-caches/`) has a registration with the same token, path, device and inode. A path, name or marker alone proves nothing; a copied, moved or symlinked tree loses ownership. Two things create ownership: the runner claims a missing or empty `target` of a Cargo project when Git ignores it (so markers never dirty the baseline), and `cache adopt [PATH]` is the explicit opt-in for an existing Cargo target (it refuses symlinks, Git metadata, non-Cargo directories, and anything containing the project or the supervisor executable). Existing unowned caches, other ktask instances' caches, and diagnostic trees such as `<tmp>/ktask-diag` are inventoried with their size and never cleaned.

**Lifecycle.** At each runner safe point (the supervisor holds the workspace lease and no worker is live) and on `cache clean --apply`, ktask retires obsolete generations of owned caches and reclaims abandoned scratch. A generation is one version of a Cargo compilation unit, identified exactly as Cargo records it in `.fingerprint/<package>-<hash>/` (`lib-<t>`, `test-lib-<t>`, `bin-<t>`, `test-bin-<t>`, `test-integration-test-<t>`…), by what it produced (executable, library or metadata only, which tells `cargo build` from `cargo check`) and by whether clippy produced it (`# env-dep:CLIPPY_*` in its dependency-info). ktask keeps the newest `keep_generations` (default 3) of each of the project's own units, so build, check, clippy and test output of the current version all stay warm, and as many incremental directories per crate as units of that crate stay (at least `keep_generations`); registry dependencies are only evicted by capacity. Output whose fingerprint is gone cannot be reused by Cargo and is retired. If the cache still exceeds `max_bytes` (default 16 GiB) or `max_files` (default 400,000), the oldest remaining generations go first, but the newest generation of every unit always stays and the pass reports `STILL OVER LIMIT` instead of wiping the warm cache. A profile whose outputs pair with no fingerprint is reported as not recognized and left alone.

**Liveness.** Nothing is removed while a Cargo build holds a profile's `.cargo-lock` (the pass is deferred and holds those locks while it runs, so a new build waits), while another cleanup holds `.ktask-cache.lock`, for any file a process has open, mapped or is executing (including the installed supervisor), for final outputs in a profile directory, for incremental sessions with a held lock, or for output newer than `grace_secs` (default 600). An interrupted cleanup removes a generation's fingerprint first, so what it leaves is output Cargo rebuilds anyway and the next pass retires it.

**Configuration.** `<config>/build-cache.json`, versioned, edited through `cache limits` or Configuration → Build cache. Values: `max_bytes` 64 MiB–16 TiB, `max_files` 1,000–50,000,000, `keep_generations` 1–32, `grace_secs` 0–7 days, `min_free_bytes` (capacity-pressure floor on the cache filesystem).

**Provider storage** (`$CODEX_HOME` or `~/.codex`, `$CLAUDE_CONFIG_DIR` or `~/.claude`, Claude Code and OpenCode data/state directories) is inventoried separately as `excluded`. Resumable session IDs, credentials and other applications' data are never cleaned: no supported scoped cleanup can prove ownership and liveness. The inventory states that these and unowned caches grow outside the bound and lists them under capacity pressure rather than claiming a global limit.
