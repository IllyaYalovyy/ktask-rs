# Run storage limits

**Principle.** A resource limit exists to stop a runaway producer from filling the host, and only that may stop work. Whatever ktask does after a producer has exited (collecting and archiving evidence, bookkeeping) is housekeeping: it completes or degrades with a visible note, and never pauses an attempt whose work and checks are sound. Limits are data the owner sees and changes in the product, they follow the project as it grows, and a breach that would repeat is not resumed unchanged.

## The limits

Limits apply per attempt or worker unless stated otherwise.

| Name | Default | Meaning | When reached |
| --- | ---: | --- | --- |
| `scratch_bytes` | 4 GiB | Logical file bytes or allocated blocks, whichever is larger, including directory blocks, in one managed worker scratch directory | stops the producer |
| `scratch_entries` | 200,000 | Files and directories in one managed worker scratch directory | stops the producer |
| `output_bytes` | 64 MiB | Persisted stdout, stderr and system text per attempt | stops the producer |
| `output_rows` | 100,000 | Persisted output rows per attempt, including empty rows | stops the producer |
| `artifact_file_bytes` | 128 MiB | Largest archived file | truncates evidence |
| `artifact_attempt_bytes` | 1 GiB | Archived bytes per attempt, including reservations | truncates evidence |
| `artifact_attempt_files` | 4096 | Archived files per attempt, including empty files and reservations | truncates evidence |
| `runner_log_bytes` | 8 MiB | One detached runner log segment; one previous segment is retained | rotates the log |

## Settings

Every limit is a stored setting with an instance default and a per-project value, each with an optional **ceiling**. The value in force is the project value, else the instance default, else the built-in default. The ceiling bounds automatic extensions, judged extensions and Raise and resume; it is the stored project or instance ceiling, else four times the configured value, and never below the limit.

- Configuration → **R Limits** lists every limit with its value, ceiling, source and the most a successful task used, and edits one limit's project and instance values (blank inherits).
- `ktask limits` lists them; `ktask limits NAME --value N [--ceiling N] [--instance]` stores a value or ceiling and `--reset` removes them. `--json` returns the same data. An agent fix may change its project's values, never instance defaults.

The supervisor and guardian read the settings again at every step, so a change applies to the next step of a paused attempt however its runner is started: CLI, TUI or background. The runner log segment cap applies when a detached runner starts.

**Test override.** `KTASK_SCRATCH_BYTES`, `KTASK_SCRATCH_ENTRIES`, `KTASK_OUTPUT_BYTES`, `KTASK_OUTPUT_ROWS`, `KTASK_ARTIFACT_FILE_BYTES`, `KTASK_ARTIFACT_ATTEMPT_BYTES`, `KTASK_ARTIFACT_ATTEMPT_FILES`, `KTASK_RUNNER_LOG_BYTES` and `<VARIABLE>_CEILING` override the stored settings of the process that has them. They exist for tests; `ktask limits` shows such a value as `env`. Invalid or zero values are ignored.

## Evidence after the producer exits

The guardian reads the whole `KTASK_ARTIFACT_DIR`; the scratch entry limit already bounds it, and there is no separate scan limit. Before archiving, the directory is moved out of the scratch that is about to be deleted. If the pass is interrupted, the runner finishes it from the kept files when it next continues, or records the evidence as truncated when they are gone.

When the files do not fit the per-attempt limits, ktask archives a deterministic selection: transcripts (text named `*.log`, `*transcript*` or `*check*`), then other text, then images, then anything else, each by name. It records a manifest of **every** file with its name, size and SHA-256, including those not archived and why (a file that is not a readable regular file has no checksum), and continues the workflow. The evidence is marked truncated and counted in Current, History and `show` (`show ID --manifest` lists the files), and given to review and validation as a fact together with `manifest.jsonl` in their evidence packet. A storage reserve or a failed copy degrades the same way. Subdirectories, links and pipes are listed and never followed.

The supervisor's own check transcripts are counted only against each other, so worker evidence cannot crowd them out. **A check transcript that cannot be archived is the one case that leaves evidence incomplete.** The check's result is already recorded: once the transcript fits, it is archived from the retained output and the check is not run again.

Supervisor notes written after work has ended are dropped, with a line in the runner log, when the output budget has no room; they never pause.

## Growth

For each project ktask records the **high-water mark** of every measured limit over successful attempts (the runner log, which rotates, has none). Configuration, `ktask limits` and the start of a new attempt warn when a limit has less than twice that headroom.

An artifact limit breached by **steady growth** (a need of at most twice the limit in force, within the ceiling) is extended to twice the limit, capped at the ceiling, without a model turn. The extension is kept for the project (source `automatic`) and does not raise the ceiling; an owner's value replaces it. A larger need is truncated as above. Scratch and output breaches while the producer runs are never extended this way.

## Pauses and Raise and resume

A pause on a limit records the limit, its value, the measured need when known, and whether the same work would pause again. Current and `show` give them with the proposed value: twice the larger of the need and the current limit, capped at the ceiling. **Raise and resume** (TUI `+`, or the button; `ktask run --raise[=VALUE]`) stores that project value and resumes the same attempt. It is refused when the ceiling does not cover the need, or a test override is set.

A plain Resume is refused with that explanation, and nothing runs, when the pause is deterministic (a check, a transcript, the cumulative output budget, or a breach that had already repeated) and neither the limit nor, where it matters, the source has changed. Stop and Restart remain available.

**The storage budget** (below) pauses the same way, but is not one of these settings: the retention policy (`retention`, Configuration → Storage) stays its only store. When its reserve refuses output or a check transcript, or blocks a launch, the pause names `storage_max_bytes` or `storage_max_files`, the smallest budget among the instance's projects, and the need: the smallest budget holding the allocation, the refused write and the reserve. Raise and resume stores this project's new maximum through the retention policy; the proposal also leaves the launch reserve free, so the resumed run can start, and its ceiling is the largest budget the policy accepts (1 TiB, 10,000,000 files). When another project's smaller budget governs, raising this one cannot help and the pause says so. A plain Resume is refused only if, after the runner's safe-point cleanup, the budget is unchanged and there is still no room: reclaimed or aged-out evidence, or a budget raised with `retention`, resumes without a raise. A queue that halts before starting a Pending task is not an attempt pause.

## Enforcement

Output and artifact admission reject a write before it enters state storage. Output bytes and rows have transactional per-attempt counters; an upgraded attempt initializes its counters from retained output once, including empty rows and UTF-8 bytes. A shared instance admission watermark serializes producers across projects and conservatively claims SQLite/WAL growth, publication directories and pending artifacts, leaving recovery headroom. Housekeeping reconciles the watermark with physical allocation when no admission intervenes. Already saved output, files, checks and history remain available. An exceeded scratch or output limit stops its producer at once and is then diagnosed (see below); only an escalation pauses the attempt as a resource condition, and raising the limit or freeing capacity permits resume without a coding repair round. A check transcript that cannot be archived is incomplete evidence and cannot pass verification.

The guardian samples managed scratch every 250 ms throughout the producer's lifetime, including after stdout and stderr close, and checks again after the producer exits. Output delivery uses bounded in-memory queues (the supervisor's reader buffers up to 1,024 chunks so a shared-database commit delayed by many concurrent projects does not back up the guardian); if the supervisor cannot accept a message for two seconds, the guardian stops the producer and reports incomplete evidence. Delivery waits do not suspend scratch monitoring. If the final message cannot be delivered, dedicated guardian exit statuses preserve scratch or delivery resource classification; the attempt pauses with an explicit incomplete-evidence reason. Resume requires fresh verification. The guardian stops and reaps the process group before archiving and cleanup. Scratch overshoot is the bytes and entries a producer can create during one 250 ms sampling interval, the directory scan, and process-group termination; the amount depends on the producer's write rate. This is a monitoring limit, not a filesystem quota. The scan short-circuits when either limit is exceeded. A detached logger process rotates stderr at a write boundary, so a segment can exceed its limit by one 4096-byte read plus the rotation marker. Existing segments are compacted to a lower configured limit at logger startup, retaining their most recent bytes and a marker. No excess output is sent to a secondary spool. A detached runner (`run --background`) never depends on its launcher's stdout: its readiness line and final message are best effort, so a launcher that closed the pipe does not fail the run.

Project Storage has a separate retained-data policy: 30 days, 8 GiB allocated and 100,000 files/directories by default (a self-hosting instance's SQLite file alone can exceed 1 GiB). The minimum age is a hard floor: capacity pressure, automatic housekeeping and manual cleanup never delete younger evidence, so when protected or too-young data keeps the instance over budget the preview and the runner report the bytes protected by age, by reused-check references and by open work, and no new work launches until capacity is raised or the evidence ages out. `retention DAYS --max-bytes N --max-files N` changes it through the shared service; Configuration → Storage offers the same fields. Byte and entry limits measure the entire opened instance state root, including the shared SQLite database, WAL, evidence directories and rotated runner logs. The CLI and TUI distinguish logical evidence bytes, physically allocated bytes, eligible files, reusable SQLite pages and protected allocation. Each runner handoff performs bounded 64-item cleanup batches and visits at most 64 directory entries for physical reconciliation. SQLite database, WAL and SHM files are measured separately at scan completion because they can be recreated behind a saved directory offset. The no-follow scan cursor survives restart; output and artifacts admitted while it runs are added to its measurement instead of restarting it, and new work waits for the scan to settle. A step launch checks the projected allocation without reading output or walking the state tree. A queued run schedules more batches while eligible cleanup or reconciliation progresses. Reused-check sources, unresolved failures, live attempts and pinned evidence remain protected. Cleanup starts before the limit, reserving up to 256 MiB and 256 entries for recovery. If that reserve cannot be kept, the runner pauses additional work and reports the current allocation and cause. SQLite's incremental vacuum is enabled for new databases. A database created with auto_vacuum off is converted once by `VACUUM` at the runner's safe point, when no work is live in the instance and about three times the database size is free; until then the preview reports the limitation and its reason. The conversion is optional: a failure or too little space in SQLite's temporary directory defers it with the cause logged and shown, and never stops the queue. Files are deleted outside SQLite write transactions, between a short transaction recording the intent and another marking them pruned; a generated-path violation is skipped and reported without stopping housekeeping. One WAL checkpoint is attempted per housekeeping call and can be deferred by a concurrent reader.

The smallest configured byte and file limits among projects in one instance govern their shared allocation. Preview reports the effective limits whenever they differ from the current project's settings. Detached runner logs use a per-project segment cap that keeps their two rotated segments inside a quarter of this shared byte budget.

## Diagnosing a breach

A scratch or output breach stops its producer at once. A check transcript that does not fit an artifact limit, and is not steady growth, is diagnosed the same way. The pause does not come first. The supervisor treats the breach like a check timeout: a read-only turn of the remediation model decides, with a reason, whether to **repair** the cause, **extend** that one limit or **escalate**. The queue stops only on escalation.

**What the model reads.** Before a scratch directory is deleted, the guardian records a bounded summary (at most 2 KiB): total bytes and entries, the five largest files, the largest directories by bytes and by entries, and how many files duplicate another file's bytes (files of equal length are hashed, largest first, within a 512 MiB read budget; a bounded search says "at least"). An output breach carries the rows and bytes per stream and the most repeated row. The model also gets a bounded transcript of the stopped work (the last 16 KiB of the attempt's output when the breach was recorded, terminal escapes removed, never archived as a new artifact), the attempt's step reports and evidence packet, and which choices are open. A scratch breach whose guardian output could not be delivered has no summary and pauses as a plain resource condition.

**Decisions.**

- `repair` resumes the executing session with the model's plan and counts as one of the ten repair rounds; with none left it escalates.
- `extend` raises that one limit for the current attempt only, by a factor of two, at most twice per limit per attempt. It never exceeds the owner's ceiling (see Settings); setting the ceiling to the limit forbids extension. It never enters a reserve: the scratch filesystem keeps 256 MiB and 256 entries free, and artifact and output limits must leave the storage budget's work reserve free. When no extension is available the decision becomes an escalation.
- `escalate` pauses with the breach and the model's reason (`Diagnosis: …`). A scratch pause does not ask the owner to free capacity, because the guardian already deleted the scratch; raise the limit instead.

A second breach of the same limit for the same cause, after a repair or an extension, escalates without asking the model again. The cause is the directory or file holding most of the scratch, the most repeated output row, or the transcript name, with digit runs ignored, so `build-1` and `build-2` are one cause. A different cause is diagnosed anew.

If the owner raises the limit above the measured use before a pending diagnosis runs, the breach is closed without one (recorded as an escalation). If the diagnosis cannot run, for example because the output limit leaves no room for it, the attempt pauses and Resume retries it; an undiagnosed output breach allows an eighth more output for the diagnosis itself.

**Record.** Each judgment is an event (`resource.breach`) with the limit, the measured use, the decision and the reason. `stats` (CLI `resource_limits` in JSON, and the Statistics dialog) reports per limit how often breaches were repaired, extended and escalated, so defaults can be revised from data.

**Worker prompt.** Execution and repair prompts state the scratch byte and entry limits in effect for the attempt, including extensions, and say that tests, builds and evidence in TMPDIR count toward them; they forbid a second copy of the project there.

For budgets below 512 MiB, a new task starts only while at least half remains free for its startup records and subsequent recovery; in-step output and artifact admission retains a separate 25% recovery reserve. The launch reserve is capped at 256 MiB, and file-entry reserves at 256 entries. Cleanup can use recently closed evidence before the launch reserve is crossed, then continues with bounded SQLite page reclamation until starting work is safe.

## Build caches and diagnostic trees

Development builds multiply: Cargo keys artifacts by package version, so every version bump leaves a full set of test binaries, libraries, fingerprints and incremental state behind. ktask bounds what it can prove it owns and reports the rest.

**Ownership.** A directory is managed only when it holds `.ktask-cache-owner` *and* this instance's registry (`<cache>/owned-caches/`) has a registration with the same token, path, device and inode. A path, name or marker alone proves nothing; a copied, moved or symlinked tree loses ownership. Two things create ownership: the runner claims a missing or empty `target` of a Cargo project when Git ignores it (so markers never dirty the baseline), and `cache adopt [PATH]` is the explicit opt-in for an existing Cargo target (it refuses symlinks, Git metadata, non-Cargo directories, and anything containing the project or the supervisor executable). Existing unowned caches, other ktask instances' caches, and diagnostic trees such as `<tmp>/ktask-diag` are inventoried with their size and never cleaned.

**Lifecycle.** At each runner safe point (the supervisor holds the workspace lease and no worker is live) and on `cache clean --apply`, ktask retires obsolete generations of owned caches and reclaims abandoned scratch. A generation is one version of a Cargo compilation unit, identified exactly as Cargo records it in `.fingerprint/<package>-<hash>/` (`lib-<t>`, `test-lib-<t>`, `bin-<t>`, `test-bin-<t>`, `test-integration-test-<t>`…), by what it produced (executable, library or metadata only, which tells `cargo build` from `cargo check`) and by whether clippy produced it (`# env-dep:CLIPPY_*` in its dependency-info). ktask keeps the newest `keep_generations` (default 3) of each of the project's own units, so build, check, clippy and test output of the current version all stay warm, and as many incremental directories per crate as units of that crate stay (at least `keep_generations`); registry dependencies are only evicted by capacity. Output whose fingerprint is gone cannot be reused by Cargo and is retired. If the cache still exceeds `max_bytes` (default 16 GiB) or `max_files` (default 400,000), the oldest remaining generations go first, but the newest generation of every unit always stays and the pass reports `STILL OVER LIMIT` instead of wiping the warm cache. A profile whose outputs pair with no fingerprint is reported as not recognized and left alone.

**Liveness.** Nothing is removed while a Cargo build holds a profile's `.cargo-lock` (the pass is deferred and holds those locks while it runs, so a new build waits), while another cleanup holds `.ktask-cache.lock`, for any file a process has open, mapped or is executing (including the installed supervisor), for final outputs in a profile directory, for incremental sessions with a held lock, or for output newer than `grace_secs` (default 600). An interrupted cleanup removes a generation's fingerprint first, so what it leaves is output Cargo rebuilds anyway and the next pass retires it.

**Configuration.** `<config>/build-cache.json`, versioned, edited through `cache limits` or Configuration → Build cache. Values: `max_bytes` 64 MiB–16 TiB, `max_files` 1,000–50,000,000, `keep_generations` 1–32, `grace_secs` 0–7 days, `min_free_bytes` (capacity-pressure floor on the cache filesystem).

**Provider storage** (`$CODEX_HOME` or `~/.codex`, `$CLAUDE_CONFIG_DIR` or `~/.claude`, Claude Code and OpenCode data/state directories) is inventoried separately as `excluded`. Resumable session IDs, credentials and other applications' data are never cleaned: no supported scoped cleanup can prove ownership and liveness. The inventory states that these and unowned caches grow outside the bound and lists them under capacity pressure rather than claiming a global limit.
