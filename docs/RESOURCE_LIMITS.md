# Run storage limits

Every value below is a positive integer environment override, read by the runner and guardian. Invalid or zero values use the default. Restart or resume after changing a limit. Limits apply per attempt or worker unless stated otherwise.

| Variable | Default | Meaning |
| --- | ---: | --- |
| `KTASK_ARTIFACT_FILE_BYTES` | 8 MiB | Largest archived file |
| `KTASK_ARTIFACT_ATTEMPT_BYTES` | 64 MiB | Archived bytes per attempt, including reservations |
| `KTASK_ARTIFACT_ATTEMPT_FILES` | 128 | Archived files per attempt, including empty files and reservations |
| `KTASK_ARTIFACT_SCAN_ENTRIES` | 256 | Most top-level artifact entries examined per worker; extras make evidence incomplete |
| `KTASK_OUTPUT_BYTES` | 64 MiB | Persisted stdout, stderr and system text per attempt |
| `KTASK_OUTPUT_ROWS` | 100,000 | Persisted output rows per attempt, including empty rows |
| `KTASK_SCRATCH_BYTES` | 4 GiB | Logical file bytes or allocated blocks, whichever is larger, including directory blocks, in one managed worker scratch directory |
| `KTASK_SCRATCH_ENTRIES` | 200,000 | Files and directories in one managed worker scratch directory |
| `KTASK_RUNNER_LOG_BYTES` | 8 MiB | One detached runner log segment; one previous segment is retained |

Output and artifact admission reject a write before it enters state storage. Output bytes and rows have transactional per-attempt counters; an upgraded attempt initializes its counters from retained output once, including empty rows and UTF-8 bytes. A shared instance admission watermark serializes producers across projects and conservatively claims SQLite/WAL growth, publication directories and pending artifacts, leaving recovery headroom. Housekeeping reconciles the watermark with physical allocation when no admission intervenes. Already saved output, files, checks and history remain available. An exceeded limit pauses the attempt as a resource condition; raising the limit or freeing capacity permits resume without a coding repair round. A check transcript that cannot be archived is incomplete evidence and cannot pass verification.

The guardian samples managed scratch every 250 ms throughout the producer's lifetime, including after stdout and stderr close, and checks again after the producer exits. Output delivery uses a bounded in-memory queue; if the supervisor cannot accept a message for two seconds, the guardian stops the producer and reports incomplete evidence. Delivery waits do not suspend scratch monitoring. If the final message cannot be delivered, dedicated guardian exit statuses preserve scratch, artifact, or delivery resource classification; the attempt pauses with an explicit incomplete-evidence reason. Resume requires fresh verification. The guardian stops and reaps the process group before archiving and cleanup. Scratch overshoot is the bytes and entries a producer can create during one 250 ms sampling interval, the directory scan, and process-group termination; the amount depends on the producer's write rate. This is a monitoring limit, not a filesystem quota. The scan short-circuits when either limit is exceeded. A detached logger process rotates stderr at a write boundary, so a segment can exceed its limit by one 4096-byte read plus the rotation marker. Existing segments are compacted to a lower configured limit at logger startup, retaining their most recent bytes and a marker. No excess output is sent to a secondary spool.

Project Storage has a separate retained-data policy: 30 days, 1 GiB allocated and 100,000 files/directories by default. `retention DAYS --max-bytes N --max-files N` changes it through the shared service; Configuration → Storage offers the same fields. Byte and entry limits measure the entire opened instance state root, including the shared SQLite database, WAL, evidence directories and rotated runner logs. The CLI and TUI distinguish logical evidence bytes, physically allocated bytes, eligible files, reusable SQLite pages and protected allocation. Each runner handoff performs bounded 64-item cleanup batches and visits at most 64 directory entries for physical reconciliation. The no-follow scan cursor survives restart; concurrent admission invalidates a stale measurement, and new work waits for a stable scan. A queued run schedules more batches while eligible cleanup or reconciliation progresses. Reused-check sources, unresolved failures, live attempts and pinned evidence remain protected. Cleanup starts before the limit, reserving up to 256 MiB and 256 entries for recovery. If that reserve cannot be kept, the runner pauses additional work and reports the current allocation and cause. SQLite's incremental vacuum is enabled for new databases; older databases keep their existing format and reuse free pages without replacing the open database. A WAL checkpoint is attempted after deletion and can be deferred by a concurrent reader.

The smallest configured byte and file limits among projects in one instance govern their shared allocation. Preview reports the effective limits whenever they differ from the current project's settings. Detached runner logs use a per-project segment cap that keeps their two rotated segments inside a quarter of this shared byte budget.

For budgets below 512 MiB, a new task starts only while at least half remains free for its startup records and subsequent recovery; in-step output and artifact admission retains a separate 25% recovery reserve. The launch reserve is capped at 256 MiB, and file-entry reserves at 256 entries. Cleanup can use recently closed evidence before the launch reserve is crossed, then continues with bounded SQLite page reclamation until starting work is safe.
