# User flows

## Screens

- Current Task — opens at startup; task details, execution controls, output, checks, and questions.
- Queue — current and pending tasks, in execution order; search, filter, and manage work.
- History — all other tasks, with results and previous attempts.
- Configuration — application settings, including mouse support.
- About — application identity and version.
- Agent reports — a dialog opened from Current Task or Projects (i) for that project: start a report or read a past one.

## Rules

- Current is running work, otherwise the first unfinished task in execution order; the first unresolved failure blocks later work. Inserting before non-running current makes the inserted task current, including when it needs approval.
- Only current can run, resume, or retry. Selecting another task only opens its details; failure blocks later work.
- Queue excludes historical tasks. Search and filters preserve execution order; display sorting is deferred.
- Done, Cancelled and Superseded are final. Copy to queue brings any of them back as a new pending task; the original stays in History unchanged.
- All user flows support mouse and keyboard. Mouse is enabled by default and can be disabled in Configuration.
- An agent report is owner-started and read-only. It is not a task, is separate from the automatic failure judge, and changes no file, task, attempt or setting.

## Task kinds

| Kind | Who does it | Project checks | Review and validation judge |
|---|---|---|---|
| AI (default) | AI agents | Yes: green baseline before the task, a check step after every implementation or fix | The diff against the Clean Code bar, with the check evidence |
| Human | The owner; confirmed with Mark done | Never | None; no AI run |
| Docs | AI agents | Never: no baseline check, no check step, and the worker is told not to run tests or builds | The written result against the goal and criteria: accuracy, completeness, consistency with the code and existing docs, clarity; a checked-in change must leave links, references and tables of contents consistent |

Every AI-run task also has a **work category** (default: code for AI, documents for Docs) that supplies the execution, review, validation and remediation templates and says whether project checks apply: code does, documents and art do not. The Docs row above is the documents category's behavior; art has the same lifecycle judged on the delivered files and the visual evidence available, with no code checks required and no image-generation tool assumed. Human tasks have no category.

A Docs task has the AI lifecycle with the checks removed: implement → review → fix → validate within one attempt, up to ten repair rounds with the read-only failure judge, then commit and delivery. Run, Resume, Retry, Stop and every other action follow the same state machine as an AI task; Run from Pending starts at implementation and Retry continues at review. The kind is chosen in the task form (CLI `--kind ai|human|docs`), filtered in Queue and History (f), shown in rows, details, `list` and `show`, and kept by import/export.

## Task states

| State | Actions |
|---|---|
| Needs approval | Approve → Pending; Reject → Pending (previous revision) or Cancelled (none); Edit, Move, Mark done |
| Pending | Run, Edit, Move, Cancel, Supersede, Mark done |
| Running (including a provider-limit wait) | Pause, Stop, Restart, Mark done; automatically → Paused (runner died), Needs input, Failed, Superseded (judge breakdown), Done |
| Paused | Resume, Edit, Stop, Restart, Mark done |
| Needs input | Answer, Edit, Stop, Restart, Mark done |
| Needs dependency | Recheck, Stop, Mark done; successful recheck → Pending before the first attempt or Paused with the same attempt |
| Failed | Retry, Edit, Stop, Restart, Mark done |
| Done, Cancelled, Superseded | Copy to queue |

- Stop returns any live task to Pending: the worker stops, the attempt ends, and uncommitted changes are saved as a git stash named `ktask: task #N attempt #M`. Run from Pending is a full restart: checks first (Docs: none), round 0, full limits.
- Restart (`T` or `ktask restart ID`) stops the current task and reaps its worker, saves uncommitted changes as a named stash, then runs it from current HEAD. An uncreated checkpoint intent is retired with a recovery event; a matching unpublished checkpoint commit is retained and rechecked. The old attempt, stash and event remain recoverable. Checks, independent review and validation run again before publication. A HEAD conflict reports expected and current commits and the restart command.
- Retry keeps the code, continues from the checks (Docs: from review), and restarts the limits. Resume continues the same attempt; after an Edit it continues in a new attempt with the new revision.
- Mark done is the owner's verdict from any unfinished state; a live attempt stops and stashes first. Only Pending can be cancelled or superseded; Supersede names at least one replacing task.
- Missing local executables, SDK components or capabilities wait for external setup. The owner
  explicitly rechecks them; only a successful bounded local probe enables Run/Resume, which probes
  again in the launching environment before checks or AI. The current
  task stays current and blocks later work without spending an attempt or repair round. Stop
  returns it to Pending and preserves its work. Other remediation remains automatic: the
  supervisor's judge repairs, revises, inserts task prerequisites or breaks the task down.
- The TUI and the CLI offer exactly these actions; a refused action names the state and what it offers.

## Flows

- Define a high-level goal, constraints, and observable success criteria → a capable execution model investigates, designs, implements, and verifies within the task → separate review and remediation models check and repair the result; separate planning or breakdown is optional.

- Open the app → inspect current task and status; an empty queue shows no current task and an Add action.
- Work on several projects from one terminal → 0 Projects (or `ktask projects` from any directory) lists every project of the instance with its state (Running, a state that needs you, Paused, Ready, Idle, Missing folder), queue size and current task, and the header counts how many are running and how many need you → select one and press Enter (or click [Enter Open] or its details) to open it; Current, Queue, History and Configuration then show that project. Each project keeps its own queue, execution order and background runner, and reopening one returns to the screen, selection and scroll it was left with. Only the open project's tasks can be changed.
- Open the app outside a project while other projects exist → Projects opens and nothing is registered → n Add this folder asks for a name and opens the new project. A registered folder, `--project DIR` and the first project of an instance open as before. A project whose folder is gone stays listed with its tasks and history, and does not open until the folder is back.
- Let Codex or Claude Code work with every project from one registration → run `codex mcp add ktask -- /abs/ktask --actor codex mcp` or `claude mcp add --scope user --transport stdio ktask -- /abs/ktask --actor claude-code mcp` once → `ktask mcp` is a host-wide stdio server that starts from any directory, creates no storage and registers no project. The `projects` tool lists every project like `ktask --json projects`; `current`, `list`, `show`, `events` and `add_draft` take an optional `project` (an ID or an absolute folder) and otherwise use the project containing the server's working directory, or fail naming the `projects` tool. Every result names its project. Each call opens its project afresh: a project with a missing folder can still be read and take drafts, and one moved or deleted meanwhile affects only the calls that name it. `--project DIR` before `mcp` pins the server to that one project and refuses calls naming another. Drafts are AI-attributed under `--actor` (default `mcp`; `--actor-kind human` is refused) and wait for the owner's approval; no approve, run, pause, stop, edit, move or delete tool exists.
- Move a project to another folder → move or clone the repository yourself → 0 Projects, select it, m Move (or `ktask project-move ID DIR`) and enter the existing folder → its tasks, history and settings follow; ktask moves no files. Refused while its runner is alive or when the folder already is a project.
- Delete a project (DANGER, permanent) → 0 Projects, select it, D Delete, type its exact name and apply (or `ktask project-delete ID --confirm NAME`) → every task, attempt, output, evidence and setting of that project is deleted with ktask's own files for it; nothing in the project's folder is touched. Refused while its runner is alive; the open project is deleted only from the CLI or after opening another one.
- Monitor current → read the situation line, the step results, and the attempt report; follow the raw log while it runs; scroll back and return to the latest output.
- Current needs input → the question is shown on screen and r Answer comes first; the answer is saved and the task continues. s Stop returns it to Pending instead.
- Current failed and not worth more attempts → D Mark done records the owner's verdict, or s Stop returns it to Pending to edit; attempts and evidence stay.
- Run current → continue the queue by default, with Run one available explicitly; see the mode, goal, current phase and next task; pause from any screen, or `ktask pause` → the runner stops gracefully and exits, with progress retained and no later task started; r Resume → continue the same attempt. From any working directory, `ktask pause --all` pauses all project runners in both instances. `ktask shutdown` also closes open TUIs for an upgrade.
- Stop a running, paused, needs-input, needs-dependency or failed task from any screen (s, [s Stop], or `ktask stop ID`) → the worker stops and is reaped, the attempt ends with its output, usage and evidence, uncommitted changes are stashed, and the task is Pending and editable. A running task completes the Stop once its runner exits; the screen never blocks.
- Declare a known local prerequisite on the current Pending task with `ktask require ID --kind executable|sdk_component|capability --item ITEM --scope task|project|host --stage STAGE --reproduction ERROR` (and optional `--version`) → Run probes it before baseline checks or AI. A missing prerequisite waits on the same Current Task, with no attempt opened. After external setup, `ktask dependency-recheck ID` or r Recheck in Current probes again; Run/Resume is separate and only available after a successful probe. The same flow handles a live worker discovery through its scoped dependency callback, preserving its attempt and edits.
- Restart the current live task (`T`, [T Restart], or `ktask restart ID`) → Stop preserves its attempt and stash, checkpoint recovery distinguishes an uncreated intent from a real commit, and a fresh run begins. Keyboard and mouse use the same confirmation and application guard.
- Set up once per user and instance → Config u (or `ktask defaults`, `ktask model-default --new-projects`) saves the role models and effort, agent network, baseline checks, check timeout, run mode, planner approval and delivery mode that new projects start with → a new project (`ktask init`) copies the settings, inherits the models live through its profile and the user defaults, applies its own overrides, detects a check where supported and lists the setup only it can supply: verification command, delivery destination, domain instructions. Check commands, directories, remotes and branches are never copied.
- Apply user defaults to an existing project → Config u, Save with "Preview applying to this project" (or `ktask defaults`) shows each current and default value → choose Apply user defaults (or `ktask defaults --apply`); until then the project keeps its settings, and existing tasks and attempts keep their pinned inputs.
- Name a model set once and reuse it → Config f (or `ktask profile create NAME --from-project`, `--model ROLE=PROVIDER/MODEL`) creates, inspects, edits or deletes a named profile such as Anthropic, OpenAI or Qwen; "New from this project's models" captures the project's current roles, for example Claude with high effort, without losing them. A profile maps roles to models the existing providers run and adds no provider; ktask checks shape and effort spelling, never availability. A profile cannot be deleted, or lose a role, while a project or the new-project default selects it.
- Choose profiles → Config f selects the profile this project uses (`ktask profile select NAME|--none`) and the profile new projects start with (`ktask profile default NAME|--none`, or Config u Default profile) → a new project (`ktask init`) selects the default profile, so projects share role settings without repeating them.
- See where a model comes from → Config d and f, or `ktask profile effective [--task ID|--new-project]`, list each role's effective model and its source in the order user defaults, selected profile, project override, task override; `ktask profile inherit ROLE|--all` (or blanking a role in Config d) clears a project override so it inherits again.
- Change a profile or selection → only tasks defined afterwards use it; existing revisions and attempts keep their pinned models, and a pending task changes only through Apply current project defaults.
- Edit models of a pending task → preview the current project defaults for execution, review, validation and remediation, then choose Apply current project defaults.
- From Queue, press r or use its Run control to start the current task, regardless of which row is selected; the selected row remains a browsing selection.
- r Retry failed current → a new attempt continues from the checks on the existing code with restarted limits, preserving previous attempts and their evidence.
- The runner dies while a task runs → the next TUI refresh or `ktask run` settles the orphaned attempt to Paused with its work kept; r Resume continues it.
- Failure inside a run → the remediation model judges the evidence and repairs within the task by default → revise, insert prerequisites, or break the task down only when the evidence warrants it; ask the owner only for a consequential product decision and require approval only by policy.
- Review a new task → approve with one action to make it ready, or reject it (a task with no ready revision is cancelled); show who approved its revision (human or AI).
- Mark done any unfinished task (D, [D Mark done], or `ktask done ID`) → record actor/reason and move it to History without rewriting its attempts.
- Configure a task → choose execution, review, validation, and remediation model/effort → save a new revision; previous attempts retain their original settings.
- Switch to another task → preserve useful changes, stop/reap processes, and clean owned temporary state before execution; a failed handoff blocks the start. Retrying the same task may keep its workspace and reuse its compatible chat session.
- Complete current → move it to History and show the next pending task as current; when none remain, show queue complete.
- Review a task through specialist lenses (concurrency, security, simplicity or your own) without separate audit tasks → Config L (or `ktask lens save|defaults`) defines lenses in the user scope, overrides them per project and picks the project's default ordered selection; the task form's Review lens fields (or `add|edit --lens NAME`, `--no-lenses`) override it for one task. A selected lens reviews the change in its own read-only session on the review model, instead of the single ordinary review; all lenses finish before one repair is requested, so several lenses neither multiply the ten repair rounds nor add an approval step, and minor observations never trigger a repair. Results name each lens and its findings in task details, History and `ktask show`. Specialist review is opt-in; the revision pins the instructions it was defined with, and a resumed attempt does not repeat a finished lens review of an unchanged source state.
- Define how a kind of work is executed, reviewed, validated and remediated → Config w (or `ktask category save NAME --scope user|project`) creates or edits a category's templates in the user scope or overrides it for this project; saving reports unknown placeholders; Preview shows the effective prompt with the task's content and labels runtime-only context → choose the category in the task form (Work category) or with `--category`. A task revision pins the templates it was defined with: later edits, overrides and deletions affect only tasks and revisions defined afterwards, never a running or resumed attempt. The supervisor's rules, evidence handling and response schema are not editable.
- Add a Docs task for documents, plans or other non-code files (task form Kind: Docs, or `ktask add --kind docs`) → it runs like an AI task, reviewed and validated against its goal and criteria, with no project checks.
- Filter Queue or History by kind (f cycles All, AI, Human, Docs) → rows of other kinds are tagged `[Human]` or `[Docs]`; the filter keeps execution order.
- Search or filter Queue → select a matching task → read its details; no matches offers clearing the search/filter.
- Add a task → save → see it appended and selected; cancel leaves Queue unchanged.
- Edit a pending, paused, needs-input or failed task → save updated details or cancel unchanged; a running task and History are read-only.
- Cancel a pending task (x) → confirm with an optional reason → it moves to History as cancelled; Copy to queue brings it back.
- Supersede a pending task (R) → name the replacing task IDs → it moves to History as superseded, linked to them.
- Reorder or insert pending work → choose an execution position → see the new order; show neighboring task IDs even when filtered. Insertion before current is allowed unless it is running; never insert into History.
- Mark done a current Human task → record completion and advance; until then, execution waits.
- Answer current AI questions → submit valid answers → record them and continue automatically; incomplete answers leave the task needing input.
- View project statistics → see task counts, completed work, failures, elapsed execution time, and cost.
- Inspect History → find a task → open Reviews or Failures directly for the selected task, or open its attempt details and select Summary, Results, Output, or Transcripts. Read each recorded review and failure step without scrolling through output; switch attempts and steps with mouse or keyboard without altering execution.
- Copy to queue a done, cancelled or superseded task from History (C) → choose a position (default: end of Queue) → a new pending task with the same definition is selected in Queue, linked to the original; the original's revisions, attempts and evidence stay in History.
- Export tasks → choose scope and destination → see success or an actionable error; confirm before overwriting a file.
- Import tasks → preview and validate → choose insertion position (default: end of Queue) → confirm; cancel or invalid input leaves Queue unchanged.
- Break down pending work → the capable model inserts ordinary subtasks in execution order → mark the original superseded and retain its attempts in History; require approval only when policy calls for it.
- Switch screens, open help, or resize → return with selection, filters, and scroll position retained.
- Change Configuration → apply valid settings or cancel unchanged; invalid settings show an error without replacing saved values.
- Open Configuration → Git delivery → choose Local, Direct push, or Pull request; set the remote and base branch using mouse or keyboard. The same versioned settings are available through `delivery` in CLI. Running attempts retain their pinned destination.
- Complete verified work in Direct mode → fetch and rebase when the base advanced → rerun checks, review, and validation → push only the verified commit to the configured base branch. A push race repeats this bounded cycle. A content conflict enters the ordinary judge/fix cycle without losing the attempt or its work.
- Commit verified work in any delivery mode → configured Git hooks run → when they change the committed content, the commit is kept and the same attempt reruns checks, review and validation on it before delivery, retaining the repair count; content committed without being in the worktree blocks delivery with the commit kept.
- Complete verified work in Pull request mode → keep queued tasks on one owned project branch → push with an exact lease for that branch → create or update its PR through `gh`. Empty changes do not create a PR. A changed remote branch owned by someone else stops delivery with the work retained.
- Open Configuration → Storage → inspect retained bytes and the exact eligible attempts → set retention days or apply the preview. Cleanup preserves Queue evidence, unresolved failures and History records; completed and partial output pruning and pruned artifacts are labeled in History and CLI. Workers and checks save flat regular files in `KTASK_ARTIFACT_DIR`; the guardian archives them per attempt before scratch cleanup (128 MiB per file, 1 GiB and 4096 files per attempt). Attempt details and CLI `show` list artifacts; CLI `artifact ID` opens text files. Later judges receive their read-only paths, checksums and source trees. The same preview, policy and apply commands are available in CLI. Interactive remediation pins its evidence through provider cleanup, including concurrent task resolution; interrupted ownership is recovered only after owner and guardian locks are idle and guardian cleanup is confirmed.
- Something went wrong, or the owner wants to know where a project stands → on Current Task or Projects press i or click [i Investigate] (or `ktask agent report [--task ID] [QUESTION]`, which prints the report's ID at once) → optionally type a question and a task ID → Apply. Without a question it explains the current state of the project and of its current task. It works whether the runner is running, paused, failed or absent, and never disturbs a live attempt or its workspace.
- While an agent investigates → its progress appears live (`ktask agent show ID`); Esc closes the view and the investigation goes on; s or [s Stop] (`ktask agent stop ID`) ends it and reaps its processes. One investigation runs per project; a second request is refused naming the running one. `ktask shutdown` stops running investigations.
- The investigator runs on the project's host in a read-only sandbox with its own scratch TMPDIR: the project folder, its Git metadata, ktask's state and configuration and other registered projects are mounted read-only. It reads a snapshot of ktask's records (tasks, revisions, attempts, events, evidence, runner log, configuration, checks, delivery, dependency waits), the project folder and Git state, and may probe the host (tool versions, disk space, processes).
- A finished report states what happened, then the cause with the events, attempts, evidence and log lines that show it (a cited event, attempt or step that does not exist is marked), then proposed fix steps, each a ktask action, configuration change, repository change, host change or owner-only decision. Nothing is applied. When the cause is a defect in ktask itself, the report says so and marks what would only work around it.
- A report that failed, timed out, passed its cost limit or was stopped is recorded as that, with what it had found, and never shown as a finished report.
- Read past reports → i, choose one in the Report field, Apply; [ and ] (or [Older] [Newer]) page through them and b returns to the form (`ktask agent list`, `ktask agent show ID`, `--json` for both). Reports keep question, requester, model, progress, token usage and cost, and are removed with their project.
- Set what one report may use → Config i (or `ktask agent limits --time-limit-ms N --cost-limit-usd X`); defaults are 15 minutes and 2 USD. The cost limit ends a Claude Code or OpenCode report; Codex reports no cost, so only the time limit bounds it. The model is the operator role (Config m, or `ktask model-default operator`), by default the remediation model.
- Open About → read application identity and version → return to the previous screen unchanged.
- Use CLI → perform the same nonvisual operations and inspect their results; screen navigation, layout, and mouse preferences are TUI-only.

- Start a task → project checks run on its clean starting commit first → a red start sends the failing evidence to the worker to repair the cause and complete the original goal; a green start begins implementation. Both require passing checks, review and validation before delivery.
- A supervisor check reaches its own timeout → ktask stops the process and preserves its transcript. The timeout covers the check command from its start to its exit, never ktask's own preparation or evidence archiving around it. The read-only remediation model uses the log to plan a fix, grant a longer limit when the check is progressing, or stop and explain what needs attention. A grant applies once per check within the current attempt, up to twice the original limit and within any remaining task time. A repair that leaves the check inputs unchanged returns to diagnosis before another run. When remediation stops, Current shows the reason and how to change the check in Configuration or with `check-set` before Retry.
- The same check fails three times with matching diagnostics on unchanged source → the remediation model plans a different repair. If that repair leaves the same failure, stop with the check and remediation evidence; Retry resets the attempt. Passing checks, changed diagnostics or changed source break this streak, while the ten-round repair limit remains. Provider and process-launch failures retain bounded backoff and the infrastructure failure limit.
- Implement → check → review → fix → validate is the normal lifecycle inside one active attempt. The configured execution model implements; the review, remediation and validation models review, plan each review/validation repair as the read-only failure judge, and validate (Claude with high effort by default). Explicit role selections are honored, including reuse of the execution model; review and validation remain separate read-only turns. A failing check goes straight back to the execution model with its failing tests and errors; critical review/validation findings start with the read-only plan. The execution model applies each fix in its own resumed implementation session, Status shows why the round runs, and checks and independent review/validation run again. Minor findings never start a round. Workers run focused tests only; the supervisor's full check run is the gate. Pause and resume preserve phase and repair round. Review findings show “fixes requested”, never a failed task. Up to ten repair rounds are allowed; after them, independent validation distinguishes concrete critical blockers from recorded minor findings. Critical blockers wait for a decision; minor notes can remain only when all mandatory criteria and checks pass.
